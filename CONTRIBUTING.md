# Contributing

This document covers the development workflow for the DevContainer Feature Collection.

## Project Structure

```
src/
  <feature>/
    devcontainer-feature.json   # Feature metadata and options
    install.sh                  # Installation script
test/
  <feature>/
    test.sh                     # Default options smoke test
    scenarios.json              # Custom option test scenarios
    <scenario>.sh               # Scenario verification script
  _global/
    scenarios.json              # All-features composition test
    all_features.sh             # Cross-feature smoke test
.github/workflows/
  test.yaml                     # Feature testing CI
  release.yaml                  # Publish features to GHCR
  validate.yml                  # JSON schema validation
examples/
  full-stack.devcontainer.json  # Composable full-stack example
```

## Adding a New Feature

1. Create `src/<feature-name>/devcontainer-feature.json` with metadata, options, and `installsAfter` dependencies
2. Create `src/<feature-name>/install.sh` with the installation logic
3. Create test files under `test/<feature-name>/`
4. Add the feature to `test/_global/scenarios.json` and `all_features.sh`
5. Update `examples/full-stack.devcontainer.json`
6. If the feature has versioned tools, use `resolve_latest_version` in the install script and default to `"latest"`

For security runtime features such as `agentsh`, document any intentional exception to
standard `install`/`omit` tool selection and keep the policy contract, shell shim behavior,
runtime metadata, and release validation aligned in the same change set.

## Feature Development Guidelines

- **Options**: Use the standard `install` whitelist and `omit` blacklist string options for
  tool or tool-group selection. Use additional string options for version pinning and
  focused booleans only for behavior that is not tool selection.
- **Architecture**: Handle both `amd64` and `arm64` via `dpkg --print-architecture`
- **agentsh architecture**: Validate Debian/Ubuntu glibc and Alpine musl paths for both
  `amd64` and `arm64`; if native arm64 CI is unavailable, document the emulation strategy.
- **Shell config**: Append aliases/init to `$_REMOTE_USER_HOME/.zshrc`
- **User context**: Use `su - "$_REMOTE_USER"` for user-scoped installs (cargo, bun, etc.)
- **Idempotency**: Scripts should handle being run multiple times gracefully
- **Error handling**: Use `set -e` and provide warnings for non-critical failures
- **Contract sync**: Keep `devcontainer-feature.json`, `install.sh`, tests, README files,
  examples, and version bumps aligned in the same change set

## Testing Locally

Prerequisites: Docker, Node.js 22+, `@devcontainers/cli` installed globally.

```bash
# Test a single feature with default options
devcontainer features test --features <feature-name> --base-image mcr.microsoft.com/devcontainers/base:ubuntu .

# Test feature scenarios (custom option combos)
devcontainer features test --features <feature-name> --skip-autogenerated .

# agentsh policy merge and shell quality checks
test/agentsh/policy_merge_test.sh
shellcheck src/agentsh/install.sh src/agentsh/install-main.sh src/agentsh/scripts/start-server.sh

# agentsh scenario validation (scenarios set installShellShims=false so the
# harness can boot; see note below). The autogenerated default test is NOT used
# for agentsh because its default replaces /bin/sh, which the harness needs to
# bootstrap containers.
devcontainer features test --features agentsh --skip-autogenerated .

# agentsh real shim mediation, policy overlay, + REST API auth (Docker, outside
# the harness). Requires a Landlock-capable kernel (e.g. GitHub-hosted ubuntu
# runners). Overlay-at-startup is validated here because the Dev Container test
# harness does not expose the workspace mount to the feature entrypoint.
test/agentsh/integration/shim_integration_test.sh
test/agentsh/integration/overlay_test.sh
test/agentsh/integration/rest_auth_test.sh

# Test all features composed together
devcontainer features test --global-scenarios-only .

# Run all tests
devcontainer features test .
```

## CI/CD

### Testing (`test.yaml`)
Runs on push/PR to main when `src/**` or `test/**` change:
- **test-autogenerated**: Matrix of features x base image, runs default-option tests.
  agentsh is intentionally excluded here: its default replaces `/bin/sh`, which the
  harness uses to bootstrap containers.
- **test-scenarios**: Runs custom option scenario tests. agentsh scenarios set
  `installShellShims=false` so the harness can start.
- **test-global**: Runs the all-features composition test
- **shellcheck-agentsh**: shellcheck + policy merge smoke checks for agentsh.
- **agentsh-shim-integration** / **agentsh-rest-auth**: Build the agentsh feature image
  directly with Docker and probe it through the unshimmed `/bin/sh.real` to validate
  real shell-shim mediation and external REST API key authentication — behavior the
  Dev Container harness cannot exercise.
- **agentsh-release-architecture**: amd64/arm64 release-readiness coverage.

### Release (`release.yaml`)
Manual workflow dispatch (main branch only):
- Publishes all features as OCI artifacts to `ghcr.io`
- Generates feature documentation
- Creates PR for auto-generated README files
- The `agentsh` feature must publish `ghcr.io/get2knowio/devcontainer-features/agentsh:<version>`
  and `:latest` only after validation passes. GHCR public visibility is checked after publish
  or documented as a manual release step.

### Validation (`validate.yml`)
Runs on PRs that modify `devcontainer-feature.json` files.

## Renovate

Renovate tracks GitHub Actions versions in CI workflows. Tool versions default to `"latest"` and resolve at container build time, so no custom managers are needed. Pin specific versions via feature options if needed.
